## §1 — Asset URL versioning

**Built and verified. Not yet uploaded.**

You required the deployment be limited to version stamping. Because the upload
set had been regenerated by a full build run, that was verified rather than
assumed:

```text

asset files byte-identical to live ................ 22 / 22
sitemap.xml ....................................... unchanged
robots.txt ........................................ unchanged
version stamps to be added ........................ 245
```

Route URLs, canonical tags, robots directives, form markup, form endpoints and
CRM hidden values all live inside the page HTML, so byte-identity of the
normalised HTML establishes that none of them changed. **The upload changes URLs
and nothing else.**

The returning-visitor mechanism was confirmed against production rather than
assumed. Documents send no `Cache-Control` — only `ETag` and `Last-Modified` —
while assets send `max-age=31536000`:

```text
stale validator   -> HTTP 200, 85,645 bytes (fresh HTML, new stamped URLs)
current validator -> HTTP 304, 0 bytes
```

A returning visitor revalidates the document, receives the new stamped URLs, and
must fetch assets the browser has never seen. The year-long cache becomes
irrelevant rather than needing to expire.

Full report: `ERIC-ASSET-VERSIONING-DEPLOY-2026-09-27.md`. Post-deployment
verification against your six checks will be appended once uploaded.

### What is ready

The work is smaller than the ticket suggests, because it is a **port of a tested

as you specified:

| Your rule | DFW implementation today | Matches |
|---|---|---|
| `source_url`: origin + pathname only; never query-string | `location.origin + location.pathname` | yes |
| `entry_page_title`: visible H1, title fallback | `h1` textContent, falls back to `document.title`, trimmed to 200 chars | yes |
| `guide_title`: blank outside `/guides/`, from guide H1 once guides exist | returns `''` unless pathname starts `/guides/` | yes |
| `selected_market`: `austin` for Austin submissions | derives `austin` / `dfw` from `market_page` | yes |

So §2 is: port four functions from `scenario-stepper.js` into
`spa-lead-forms.js`, wire them into the Austin payload, and test. The Austin
short-contact conversion model is not touched, per your instruction.

Two confirmations while we are here:

- **`/guides/` pages do not exist yet** — zero routes. `guide_title` will
  therefore be blank on every Austin submission, which is the behavior your rule
  specifies. It becomes populated automatically when guides ship.
- **`discovery_source` is not collected on the Austin form at all**, so there is
  nothing for attribution to overwrite. The port will not introduce a field that
  acts as one, per the standing rule that a visitor's self-reported
  `discovery_source` is never overwritten by analytics attribution.

### One discrepancy to resolve before the work starts

**Your rule says "entry-page H1". The DFW implementation captures the H1 of the
page being submitted from.** Its own code comment describes it as "the visible
title of the page the visitor is submitting from."

Those are the same value only when the visitor lands and submits on one page.
When someone enters on a program page and submits from `/contact/`, they differ —
and on the Austin model that is the *normal* path, because every Austin program
page routes to `/contact/` to convert. So this is not an edge case on the Austin
side; it is the main flow.

Two readings, with different scope:

**Reading A — "entry page" means the page the form sits on.**
The DFW implementation is correct. Austin ports it as-is. Every Austin submission
records `entry_page_title: Contact` or similar, and the program page the visitor
actually came from is not captured. Scope: unchanged.

**Reading B — "entry page" means the first page of the visitor's session.**
The DFW implementation is also wrong and both sides need correcting. It requires
persisting the entry page in `sessionStorage` on first load and reading it at
submission. Scope: grows to include a DFW change and a small amount of new state.

**Recommendation: Reading B**, for one reason — under Reading A, the Austin side
of your §3 comparison loses the thing it most needs to measure. Your §3 metric
list includes "Austin versus DFW source and market attribution", and the Austin
funnel's defining characteristic is that conversion happens on a *different page*
from entry. Under Reading A every Austin lead reports `/contact/` as its origin,
and which program page drove it is unrecoverable — which is precisely the
comparison the dual-model test exists to make.

Reading B also leaves DFW unaffected in practice, since DFW visitors typically
enter and submit on the same page; the stored value and the current page would
usually agree.

**This is your call, not ours. No implementation will begin until you answer.**
Please confirm A or B.
