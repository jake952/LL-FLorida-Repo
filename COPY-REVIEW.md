## 3. A ratings claim in structured data — site-wide, live now

Different from everything above: this is not copy, it is not on one page, and
it is not something this project introduced. It needs a decision that reaches
further than the pages here.

**What it is.** The `MortgageLender` JSON-LD block carries:

```json
"aggregateRating": { "@type": "AggregateRating", "ratingValue": "5.0", "reviewCount": "251" }
```

**The rule.** "Ratings claim — do not mirror into schema"
(03-self-employed.md:1137). Visible ratings copy is already flagged in the
hero table above (`Five-Star Reviews`, `5.0★ Google & Yelp Rating`); this is
the same claim published as machine-readable data, which is what search and
answer engines read and may display as a rating snippet.

**Where it is.** In the single-page-app shell that every React route serves,
so it is on every Austin URL live right now — not just the pages in this
project. It is not in the index.html this package uploads.

**Fixed in this package, not yet live (7 September 2026).** `aggregateRating`
was removed from the shell schema on instruction, so once this deploys no
route will publish the claim - not the React routes and not the 8 static
Austin pages. The rest of the
`MortgageLender` record is untouched: name, telephone, address, founding date
and all 14 `areaServed` entries survive, and the block was re-parsed to prove
it is still valid JSON. A malformed block would have been worse than a
non-compliant one, because engines drop the whole organization record rather
than just the rating.

Two build gates now refuse to ship it back: one in `build-package.js` for the
shell, one in `build-austin-programs.js` for the static pages.

**Still open:** the visible ratings copy — `Five-Star Reviews`,
`5.0★ Google & Yelp Rating` — is still on the pages and still flagged in the
hero table above. Removing the claim from schema while leaving it in copy is a
defensible position, but it is a position rather than an oversight, so it is
worth confirming that is what was intended.


## 4. Imagery that implies a price tier

The only item here that is not a phrase. The claim exists in a pairing: the
photograph claims nothing on its own, the headline on its own is approved
copy, and together they imply a price bracket. There is no sentence to
quote, so it cannot be a row in the tables above.

**What it was.** The closing CTA on the market home ran an aerial of
multi-million-dollar waterfront estates with infinity pools — the Lake Austin
corridor. (Despite the filename, `austin-skyline-home.webp` contains no
skyline.) It sat directly behind the headline:

> **"Your Tax Returns Shouldn't Define Your Dream Home."**

Read as one unit, which is how a visitor reads it, the composite says: that
is the dream home, and your tax returns will not stop you getting it.

**The rule it leans on.** "No approval, rate, payment, closing-time,
credit-score, down-payment, loan-limit, reserve, or eligibility promises,"
plus the bar on "similar universal-product claims". The photograph states no
loan limit, but it implies a ceiling — in the one place on the page where the
headline is already about tax returns.

**Why it compounds.** The market home already carries tier claims in copy,
each flagged separately in the tables above:

- `$1.4M` — appears 3 times
- `luxury properties`
- `No Tax Returns Required`

So the copy already sets an implied ceiling around $1.4M. The photograph set
one visibly higher than anything approved, and reinforced in a picture the
same claim the copy rules bar in words.

**The practical risk is expectation-setting,** not litigation over a stock
photograph. A self-employed borrower with a $450K budget sees estates plus
that headline and infers a larger loan than they will qualify for. The rules
already guard the other direction — "no form response triggers an automatic
decline, eligibility result, or discouragement" — and over-promising is the
same problem inverted. It is also an audience mismatch: this page's borrower
is a bank-statement applicant, and estates are the aspirational tail rather
than the median case.

**How much weight this deserves — stated plainly, because it is weaker than
everything else in this document.** Nothing in the handoffs mentions
photographs, so this is an inference from a copy rule's intent applied to art
direction, and a picture is much harder to characterize as a representation
than a sentence is. The counter-argument is only that the rules exist for
whole-page exposure, and a reader does not segment copy from imagery. Raised
as a judgment call for you, not as a defect found.

**Changed in this package, not yet live (8 September 2026).** The market
home's closing CTA now uses `suburban-neighborhood-aerial.webp` — an ordinary detached
subdivision, which implies no tier in either direction and matches the actual
borrower. Behind the section's 80% navy overlay it reads as neighborhood
texture. Note that the swap was justified on two firmer grounds regardless —
Austin imagery on the DFW-targeted page, and repetition with the about-page
hero — so it did not wait on this decision.

**Still open: the same photograph is the hero of the DFW about page.** Left
there deliberately. The framing is company-and-location rather than "your
dream home", so the implied-product reading largely goes away, and an Austin
photograph belongs on the page about an Austin-based company. But that is a
judgment, not a rule: if estates imply a tier anywhere on the site, that
page is the other place to change. **One decision covers both pages.**

Its alt text was corrected either way — it read "Austin skyline" for a
photograph containing no skyline, which was simply wrong for anyone using a
screen reader.

**What each outcome means.** Approve the estates imagery and this item closes
with no work — say so and I will record it as reviewed. Reject it and the
about-page hero needs a replacement too, which is one image search. Either
way the market home stays as it is now, because it was changed for the market
and repetition reasons rather than this one.


## 5. One British spelling inside consent language

A one-word decision, in this document only because of where the word sits.

**The string.** The contact form shows this when someone submits without
ticking the consent box:

> Please review and accept the contact authorisation to continue.

`authorisation` is the British spelling. Everything else on the site was
converted to American spellings on 9 September 2026 at the client's
instruction — 96 replacements across the docs and builders. This string was
the single exception.

**Why it was left.** Your rule: "Include only legal/consent language
supplied by the approved CRM/compliance implementation. Do not invent TCPA,
SMS, or consent text." A spelling normalization invents nothing, but it is
still an edit to consent wording on a page carrying an NMLS ID, and that is
yours to make rather than something a housekeeping pass should decide. It is
the only place in the project where the spelling instruction and a
compliance rule pointed in opposite directions, and the compliance rule won.

**What is being asked.** Approve changing `authorisation` to
`authorization` in that one message. No other word changes, and the meaning
is identical. If you would rather it stay as it is, that is fine too — say
so and I will record it as reviewed so nobody re-raises it.

**Where it lives if approved:** `scratchpad/build-dfw-contact.js`, which
emits the contact page. There is a guard in the spelling tool naming this
string, so it will not be changed by accident either way.
